## 2. Transaction highlighting

**The ask.** An alert raised on a high transaction amount should highlight that transaction in the full ledger. An alert raised on unusual card origin should highlight every transaction that could have contributed — *and highlight the card origin as the reason that transaction is highlighted*.

**What was there.** The ledger marked rows exceeding the merchant's own amount threshold, computed at render time, regardless of which detector actually fired. A card-origin alert highlighted amount outliers, which is the wrong rows for the wrong reason.

**What changed.** Every detector now returns, alongside its score, the transactions that drove it and the **source column** of each that carries the cause. The ledger highlights exactly those rows and marks exactly that cell, with the reason on hover.

| Alert | Rows highlighted | Cell marked |
|---|---|---|
| Amount anomaly | the transactions that breached | `total_amount` |
| Card origin | every transaction on a surprising issuing country | `card_issuing_country` |
| Structuring | the transactions inside the near-threshold band | `total_amount` |
| Decline spike | the refused authorisations | `transaction_status` |
| Out-of-hours / geo-velocity | the transactions at the implicated time | `occurred_at` |
| Merchant-level peer, trend | **none** — the merchant is the subject, not any transaction | — |

Three decisions worth recording:

- **Silence is meaningful.** An empty evidence set is a positive statement that no transaction is the reason — different from "we did not look". The ledger says so in words rather than showing an unexplained absence of highlighting.
- **Highlighting follows the indicator in focus.** Colouring every row any detector ever touched would be no highlighting at all.
- **Evidence is frozen onto the alert**, not recomputed on read — the same reason `feature_snapshot` is. A later run with retuned thresholds would otherwise rewrite what the analyst was shown.

## 3. Family B — the typology ruleset

Seven rules, each a named test with explicit parameters: structuring, refund abuse, bust-out, dormant reactivation, rapid movement, declared-vs-actual mismatch, decline-ratio spike. Exact conditions and defaults in [§4a](../Detection_Flow_Diagrams.md).

**Every rule carries a second condition**, and that is the interesting part. A single-condition rule floods the queue:

| Rule | Without its guard |
|---|---|
| Structuring | fires daily on any jeweller whose ordinary sale is near the line |
| Refund abuse | fires on a single return |
| Bust-out | fires on every merchant that grows |
| Dormant reactivation | fires on any shop reopening after a holiday |
| Declared vs actual | fires on a merchant that is merely expensive for its trade, which is legal |
| Decline spike | turns three declines out of four into a 75% rate |

### The tuning surface

The feedback asked for an interface to manipulate the rules and add their own, with the tuning sections differentiated. The Tuning screen now splits into three tabs, because the families are tuned as genuinely different kinds of thing:

- **Family A** — a handful of global statistical thresholds. Sliders.
- **Family B** — a *set* of named rules, each of which can be retuned, scoped to an MCC, switched off, or duplicated with the officer's own parameters.
- **Family C** — the same, minus scoping: a ring spans merchants of different categories by nature, so an MCC scope on one would quietly exclude half the ring. The API rejects it.

Each rule shows its **rationale** beside its controls — a rule that cannot say why it is built that way is not defensible to a regulator, and it should not live in a document nobody opens. Each parameter states what moving it costs, because a threshold with no stated trade-off invites turning sensitivity down until the queue is empty, which is not the same as having no risk.

**Rules are templates instantiated with parameters, not free text.** An officer adds a rule by taking a pattern and giving it their own parameters and scope — "structuring, but HKD 100,000 and only for jewellers" — running alongside the portfolio-wide instance. A free-text predicate language was deliberately not built: it would be an arbitrary code path into the detection engine, and an AML rule nobody can statically review is not auditable.

## 4. Family C — ring detection

Five rules: shared merchant identity, onboarding-agent concentration, one card across related merchants, card swarming, impossible geo-velocity. Exact conditions in [§5.4](../Detection_Flow_Diagrams.md).

### The two questions the feedback asked directly

**"What is the structuring threshold across branches?"** Your suggestion — one card, at most three branches of the same merchant in a single day, alert on the fourth — is implemented as stated and is the shipped default. Two clarifications:

- The source schema has **no `terminal_id`**, so "branches of the same merchant" can only be expressed as distinct `merchant_id`s sharing an identity hash. That is the only form of the idea the data supports, and the flow diagram now says so.
- It is a hard count rather than a statistic, deliberately. There is no natural distribution to fit here, and a count a compliance officer can defend in a report beats a z-score nobody can explain.

**"How will impossible geo-velocity be checked, and where does distance come from?"** Distance between subdistrict centroids ÷ elapsed time, against a committed coordinate table.

- **The table is committed, not fetched.** `backend/src/compliance/data/hk_geo.json` carries a centroid for every subdistrict in the extract plus a district fallback. Coordinates rather than a precomputed N×N matrix: 106 points is a 4 KB file where the matrix is 11,236 entries, and a new subdistrict costs one line. A detector whose answer depends on a maps API is not reproducible for audit and cannot run air-gapped.
- **The threshold is 60 km/h, not 1.5 m/s.** 1.5 m/s is walking pace — slower than the journey actually takes — so it would flag essentially every card used in two districts on the same day. Hong Kong door-to-door speed is bounded by MTR and road traffic, so 60 km/h is already generous, which is the right direction for a rule that accuses a card of being in two places at once. It is tunable.
- **The bias is toward under-flagging.** Centroid distance ignores terrain, harbour crossings and routing, so it is a lower bound on the journey and therefore on the implied speed. Same-subdistrict pairs read as 0 km and can never fire. A 3 km floor keeps the rule out of the range where centroid distance is meaningless. Two transactions at the same recorded minute yield *no* speed rather than an infinite one — a zero-second gap is clock resolution or a batch import, not supersonic travel.

### Scope change, recorded not buried

The detection-layer spec **§5.3 explicitly placed impossible geo-velocity out of scope** as cardholder fraud rather than merchant integrity. feedback03 asked how it would be checked. Rather than silently contradict the spec, the reversal is written into it with its justification: a card that cannot have been present at both merchants means at least one of them accepted a card that was not there, which is a merchant-acceptance question. The output is a ring signal, not a fraud verdict. BIN / card-testing stays out; the merchant-side substitute is the Family B decline-ratio rule.

### The PAN hash

`hashed_pan` is 1:1 and unsalted, so it is brute-forceable back to a card number — cardholder data, not a safe token. It is read **only** inside `detection/rings.py`. Every piece of evidence Family C produces names the counterpart merchant and the transaction ids, never the identifier that linked them: an analyst can see that one card connected two merchants without being handed the card. Enforced by test, not convention.

> **Gating.** The card-linkage rules are built and tested, but §5.2's security treatment — HMAC re-hashing or a decision that the source hash is PAN-equivalent, encryption at rest, access control, PDPO sign-off — is **not yet in place**. These three rules should run in shadow until it lands. Recorded in the spec's build order.

## 5. Bugs found on the way

- **The hour detectors read the wrong window.** `_scored_day_hours` filtered on `occurred_at >= as_of` — unbounded, and starting *after* the scored day rather than during it. This is the same class of bug the scored-day fix addressed in feedback01, missed in one helper. Both hour detectors were examining data no other detector looked at, and usually nothing at all.
- **Alert ranks were not reproducible.** Ties on `sub_score` left rows in whatever order the query returned them, so two runs over identical data could assign different ranks — a column the audit trail carries. Now broken on merchant then detector.
- **A first run could never detect a ring.** "Members already flagged" was read from the alert table, but alerts are not written until the final stage, so on a fresh run nothing was flagged and every ring sat silently below threshold. Family C now also reads what Families A and B found in the same run.

## 6. Verification

- **241 backend tests pass** (was 157), including 15 end-to-end assertions that each planted typology and ring is found *and that the well-behaved control merchants are not* — a detector that fires on everything passes a "did it fire" test and is useless.
- The geo coverage test runs against the **real 1.9 GB extract** and asserts every district/subdistrict pair resolves to a coordinate; a missing place would silently disable geo checks for every merchant in it.
- Frontend builds clean.
- **Full pipeline run on generated history: 63 alerts across all 20 detectors in all three families**, every alert carrying either a feature row or a message, and evidence attached wherever a transaction is the reason.
- UI verified in the browser: the structuring case highlights the four near-threshold transactions with the **amount** cell marked; the card-origin case highlights the overseas transactions with the **issuing country** cell marked; the geo-velocity case highlights the transaction with the **time** cell marked and explains the 35.4 km in 20 minutes.

### Measured against the real extract

**`hashed_pan` is present on only 48% of transactions, and the split is by payment rail.** Card schemes (Visa, Mastercard, Amex, JCB, and 85% of UnionPay) carry it; wallet and stored-value rails (Alipay, Octopus, WeChat, PayMe) carry none — they have no card number to hash. Those four rails are **52% of the extract**.

This is a real detection gap, now written into [§5.7](../Detection_Flow_Diagrams.md) rather than left to be discovered by an analyst wondering why a ring was missed:

> Every card-linkage rule — branch structuring, card swarming, geo-velocity — is **blind on wallet rails**. A ring transacting exclusively on Octopus is invisible to Family C's card sub-layer. The merchant-identity layer is unaffected and covers every merchant regardless of rail, which is a further reason it leads.

A second limit: **85% of cards appear exactly once** in the extract, ~3% three times or more. The card-linkage rules are looking for a rare shape in a sparse graph — appropriate for a ring signal, not a layer that will produce steady volume.

### Not verified

The pipeline has **not** been run end-to-end against the full 1.9 GB extract in this round; detection quality is measured on the synthetic generator, which is where the ground truth lives and is a lower bound on difficulty rather than an estimate of production performance. The thing that most wants real-data validation before these rules reach a live queue is whether the Family B defaults produce a workable alert volume at portfolio scale — the guards are designed to keep it low, but "designed to" is not "measured at".
